# SAS2308 kext: final review (sas2308-dext @ 1b69304)

Read-only review. Inputs: the five area reviews in this directory, the code at HEAD
1b693049dd240e2c14d0893e884e942b826e4370, Apple's IOSCSIParallelFamily / SAM / xnu sources in the
local copy (`src/`), FreeBSD `ref/freebsd-src/sys/dev/mps`, and the panic report
`panic-full-2026-11-20-031715.panic`. Every finding of the area reviews was checked against the
code; "confirmed" below means I traced the path myself. Nothing was run on hardware.

## 1. Executive summary

**Overall risk: high for anything other than supervised use with scratch disks.** The normal IO
path (submit, complete, chain SGLs, DMA mapping) is sound and I found no bug that corrupts data in
steady-state IO. The defects are in what happens when something goes wrong or changes: a lost
reply, a reset, sleep, restart, hot-plug, a disk swap.

- Two critical defects: (C1) no IO ever times out, so all of the recovery code is unreachable and
  a single lost reply hangs its issuer for good; (C2) a target nub is tied to the firmware device
  handle only, so a different disk in the same bay after sleep / reinit silently inherits the old
  disk's mounted volume.
- Five high: lost hot-plug work (thread-call re-entry, the 4d64411 class again), a lost or doubled
  reinit request, the missing arm64 barrier before doorbell writes, device removals dropped when
  more than 4 go at once, and the shutdown path (IO held for ever after the shutdown quiesce).
- Counts after verification and dedupe: **critical 2, high 5, medium 8, low 17**. Refuted 1,
  downgraded 4.

**Is it safe to keep the current build running for the benchmark (scratch disks, no sleep, no
reset, no hot-plug)? Yes. Nothing found warrants stopping the benchmark.** Reasons and conditions:

- None of the critical/high findings is triggered by steady IO. C2, H1, H2, H4 need a hot-plug,
  reinit or sleep. C1 turns a lost reply into a hung benchmark thread, not into corruption.
- H3 (barrier) is the only one that could in principle corrupt data during plain IO. The window is
  nanoseconds against a Thunderbolt round trip of microseconds, and the data is scratch. If the
  benchmark verifies data, a mismatch should be read with H3 in mind.
- Conditions to keep it safe (worth checking now, without interrupting the run):
  1. The Mac must not go to sleep. An ssh-driven benchmark does not hold a sleep assertion; check
     `pmset -g assertions` / run under `caffeinate -s`. Sleep/wake has never run on hardware and
     hits M1, M8 and C2.
  2. Do not unplug the dock, swap a disk or replug a breakout during the run.
  3. Do not `shutdown -r` with the kext loaded and disks attached (section 5): unmount the scratch
     volumes and `kmutil unload` first, or power the dock's drives down first.
  4. If the log shows `Reinitializing controller` during the run, discard the results and do not
     trust the contents of the scratch disks (C2 is then possible; so is a hang, H2).
  5. If a benchmark thread hangs with no error, that is C1: only an unload or a sleep/wake frees
     it; nothing in the driver will.
- No disk that holds data anyone cares about should be attached to this build.

## 2. Verified findings, ranked

File:line refer to HEAD. "Host test" says what would have caught it.

### C1 (critical, confirmed) The family's task timer is never armed; no IO times out

- **Where:** `kext/SAS2308HBA.cpp:706-839` (`ProcessParallelTask` never calls
  `SetTimeoutForTask`; `grep -rn SetTimeoutForTask kext/ core/` is empty);
  `kext/mps_xnu_os.cpp:907` (`ccb_h.timeout = 0`), so `core/mps_sas.c:1606-1608` arms no core
  callout either.
- **Apple source:** `IOSCSIParallelInterfaceController.cpp:1619-1626` `SetTimeoutForTask` is the
  only caller of `SCSIParallelTimer::SetTimeout`. `ExecuteParallelTask` (`:1299-1315`) only calls
  `ProcessParallelTask`; `IOSCSIParallelInterfaceDevice::SendSCSICommand` (`:1202-1340`) does not
  arm anything. `TimeoutOccurred` (`:1635-1663`) only walks tasks that were put on the timer.
  Apple's own HBA does it in ProcessParallelTask (`iscsi.cpp:621`). The copy in a local copy is
  family 3.0.0; `SetTimeoutForTask` is protected API of the class, so the contract is the same in
  the shipping family.
- **Consequence:** `HandleTimeout` → `mps_kext_timeout` → `mps_xnu_ccb_timeout` never runs. Abort →
  LUN reset → target reset → reinit, the held-IO timeout and `familyTimeouts` are dead code on
  hardware. `docs/design.md:731-733` ("The family's per-task timeout keeps running for held
  tasks") is false. Upper-layer waits are `THREAD_UNINT` with no deadline
  (`IOSCSIPrimaryCommandsDevice.cpp:1250`), so one lost reply (dropped MSI, SATA disk that stops
  answering) blocks its issuer for ever: a filesystem thread, or the hotplug thread inside
  `CreateTargetForID`'s synchronous probe, which then blocks `willTerminate` → unplug/unload hang.
  IO held by the thin CAM (reinit pending, suspend, shutdown, startup) has no bound either.
- **Fix:** in `ProcessParallelTask`, after the slot is taken and before `mps_kext_submit`, call
  `SetTimeoutForTask(task)` (0 = the task's own timeout). Only `CompleteParallelTask` removes the
  timer entry (`:1359`), so once armed never return a non-In_Process response: queue a
  synchronously refused task on the done queue and complete it through `DeliverCompletions`
  (this also fixes L2 below). Add a core backstop: a non-zero `ccb_h.timeout` (family timeout +
  10 s) so the FreeBSD callout still fires if the family timer is ever lost.
- **Test:** hardware: `sas2308ctl`-triggered "drop next reply" fault injection (add one), expect
  `Family timeouts` to count and an abort in the log. Host: compile the kext glue against a fake
  family (TF1) whose timer only fires for tasks passed to `SetTimeoutForTask`; the existing
  timeout tests then fail until the call is added.

### C2 (critical, mechanism confirmed) A nub survives a change of the disk behind it

- **Where:** `core/mps_xnu.c:441-464` (`mps_xnu_get_tid`: a tid is given back when
  `tid_handle[i] == handle`; nothing compares SAS address, device name or disk identity);
  `core/mps_sas_lsi.c:375-383` (the only caller; the comment says so);
  `core/mps_sas.c:826-834` (reinit zeroes handles, keeps targets);
  `kext/SAS2308HBA_Targets.h:52-57,82-84` (lost + present coalesce into "keep the nub").
- **What the firmware does here:** `docs/design.md:504-505` shows PHYs 0, 2, 3 ↔ handles 0x9,
  0xb, 0xc, so on this IT firmware a direct-attached handle follows the PHY (bay), not the disk.
  That makes the area review's "handles permute after a diag reset" trigger unlikely, and makes
  the following one certain: **the same bay always yields the same handle, hence the same tid and
  the same nub**. For SATA the IOC-made SAS address also follows the PHY, so even a SAS address
  check would not help.
- **Failure scenario:** the dock keeps the drives powered while the Mac sleeps. Disk A (mounted)
  is replaced by disk B in the same bay during sleep. Wake → reinit → rediscovery finds handle
  0xb → tid 2 → the wildcard rescan reports tid 2 present → nub 2 is kept. A's mounted volume now
  reads and writes B. The same happens if the swap falls into a reinit, or if the destroy of the
  old nub is lost or still queued (H1, H4, or the hotplug thread stuck in a probe because of C1)
  when B appears.
- **Fix:** port FreeBSD's `mpssas_get_sas_address_for_sata_disk` (IDENTIFY-derived id; in
  `ref/.../mps_sas_lsi.c`) so `targ->sasaddr` identifies the disk; key `mps_xnu_get_tid` on that
  id instead of the handle; keep a per-tid generation that changes whenever the identity changes
  and pass it with the async event; in the kext a generation change forces destroy-then-create
  and is never coalesced. Until then the safe interim is: after a resume or reinit destroy and
  re-create every nub (volumes are ejected, nothing is cross-wired).
- **Test (host):** mock: reinit, then re-announce handle H with a different disk identity; assert
  that the target table yields destroy + create for that tid. `kext_targets_test` currently
  asserts the coalescing as intended behaviour.

### H1 (high, confirmed) Hotplug thread call re-entry loses a create/destroy

- **Where:** `kext/SAS2308HBA_Hotplug.cpp:83-90` (`thread_call_enter` while an invocation runs
  starts a second one), `:111-146` (forward-only `cursor`), `kext/SAS2308HBA_Targets.h:69-90`
  (`Next()` skips busy targets without consuming the wish). Same class as 4d64411.
  (callouts H2 = memory-testfidelity H1.)
- **Scenario:** A is inside `CreateTargetForID(5)`; the drive drops; `Update` records
  `fWantDestroy(5)` and kicks; B scans, skips 5 (busy), exits; A finishes with its cursor at 6.
  Nub 5 stays for a removed disk (and feeds C2), or a quickly re-plugged disk never appears.
- **Fix:** `fHotplugActive` / `fHotplugAgain` under `fLock` (the `tq_active` pattern): a re-entered
  invocation sets "again" and returns; the active one rescans from 0 until nothing is pending.
- **Test (host):** in `kext_targets_test`, run a second `Next()` loop between the first loop's
  `Next` and `Done` (TF1 thread-call model); today the wish is lost.

### H2 (high, confirmed path) A reinit request made during a reset is lost or doubled

- **Where:** `core/mps.c:805-809` (the "Reset already in progress" return is before
  `reinit_pending = 0`), `core/mps_xnu.c:585-595`, `core/mps.c:2955-2958` (`mps_wait_command`
  runs `mps_reinit` inline on the event thread), `core/mps_sas.c:867` (`mpssas_tm_timeout`
  requests unconditionally). (locking F1+F2 = callouts H1.)
- **Scenarios:** (a) inline reinit from a config-page timeout drops mps_mtx in
  `mps_diag_reset`; a TM timeout callout sets `reinit_pending` and queues the task; the task sees
  DIAGRESET and returns with the flag still 1. Every new IO is then requeued
  (`mps_sas.c:1484-1485`), OS TMs get CAM_BUSY (`:2218`), fault detection is off
  (`mps.c:1885`, `mps_xnu.c:603`): permanent IO outage. (b) the running reset is the task itself:
  a TM timeout during it re-queues the task and a second full diag reset follows.
- **Reachability today:** TM timeouts need timed-out IO, which C1 prevents, so (a)/(b) are
  currently reachable only through OS-requested TMs. **Fixing C1 makes this live; fix both
  together.**
- **Fix:** clear `reinit_pending` at every exit of an `mps_reinit` that ran; `mps_reinit_task`
  returns when the flag is 0; `mps_xnu_request_reinit` ignores requests while DIAGRESET is set
  and `!suspending` (FreeBSD's "the reset in progress covers it").
- **Test (host):** time out a config read with a TM outstanding whose callout expires inside the
  diag-reset sleep; assert `reinit_pending == 0`, one diag reset, IO flows.

### H3 (high, latent; confirmed by reading, not observed) No barrier between DMA-memory stores and MMIO

- **Where:** `kext/mps_xnu_os.cpp:316-321` (plain volatile store); `bus_dmamap_sync` is empty.
  Ordering users: `core/mps.c:1243-1246` (request frame → descriptor post),
  `core/mpsvar.h:536-542` (free queue → REPLY_FREE_HOST_INDEX), `core/mps.c:2221,2363` (post slot
  cleared → REPLY_POST_HOST_INDEX). (dma-mmio F1 = memory-testfidelity H2.)
- **Why:** ARMv8 does not order a store to Normal memory before a later store to Device memory.
  FreeBSD mps relies on x86 ordering; Linux `writel` issues `dmb oshst` for this.
- **Scenario:** the IOC fetches the frame for a SMID before its last stores are visible and runs
  a stale CDB/SGL (wrong data, or a DART fault on an unmapped IOVA). Probability per IO is very
  low; the class is data corruption.
- **Fix:** `__asm__ volatile("dmb oshst" ::: "memory")` before the store in
  `mps_os_bus_write_4`, `dmb oshld` after the load in `mps_os_bus_read_4`.
- **Test:** not observable on the host; add the barrier contract of TF5 (the mock fails a
  doorbell write that follows a DMA-memory store without a barrier hook call).

### H4 (high, confirmed) Removal dropped when no high-priority command is free

- **Where:** `core/mps_sas.c:305-312` (`INREMOVAL` set, `mpssas_alloc_tm` fails, return before
  `mpssas_rescan_target`); pool of 4: `core/mps_xnu.h:27`, `core/mps.c:358-365`. The events of
  one burst are handled in one pass under mps_mtx (`mps_sas_lsi.c:176-200`), so no TM can complete
  in between. (cam-family H1.)
- **Scenario:** the drive enclosure loses power (7 disks): removals 5-7 never rescan. Their nubs
  and mounted volumes stay, the tid keeps `handle != 0` and INREMOVAL for good, the firmware
  never gets REMOVE_DEVICE, and a returning disk gets a second target with the same handle
  (`mpssas_find_target_by_handle` then finds the zombie first).
- **Fix:** call `mpssas_rescan_target` before the allocation, queue removals that found no TM and
  start them from `mpssas_free_tm` (as `mpssas_xnu_retry_recovery` does for aborts); raise
  `MPS_XNU_PRI_REQ_FRAMES` to 8 or more (bounded by HighPriorityCredit anyway).
- **Test (host):** mock: 7 TARG_NOT_RESPONDING in one event batch; assert 7 rescans/absent and 7
  REMOVE_DEVICE.

### H5 (high, confirmed by reading; link to the observed panic plausible) Shutdown path

See section 5 for the panic. Code facts, all still in HEAD (`git diff 51a6940 HEAD` is empty for
`kext/SAS2308HBA_PM.cpp`, `kext/SAS2308HBA.cpp`, `core/mps.c`):

- `kext/SAS2308HBA_PM.cpp:120-129`: `systemWillShutdown` runs `QuiesceController` synchronously
  and then calls `super` (so it is acknowledged; that part is correct).
- After it, `sc->xnu.suspending` stays 1 for good (`fShutdown` blocks the resume,
  `SAS2308HBA_PM.cpp:108`). Every IO that arrives later, and every R/W retry of IO that the quiesce
  failed with CAM_SCSI_BUS_RESET, is requeued and held (`core/mps_sas.c:1484-1496`) and, with C1,
  never completes. Any Apple thread waiting for such a task sleeps uninterruptibly for ever with
  no frame in our kext.
- The quiesce itself is not bounded against the 30 s halt watchdog: 2 s drain, then
  `mps_transition_ready` (`core/mps.c:986`): MUR ack up to 5 s, and if the IOC is not OPERATIONAL
  or the MUR fails, `mps_diag_reset` (up to 300 s) inside a 1200-try loop
  (`core/mps.c:242-300,152-185`). Same for `setPowerState(off)` with a 10 s drain (locking F6).
- **Fix:** shutdown is not sleep. In the shutdown variant: no drain beyond ~1 s, MUR once with a
  short ack wait, on failure `mps_os_controller_dead` (bus mastering off) and no diag reset; then
  fail everything held and everything that arrives later with DeviceNotPresent instead of holding
  it (set a `shutdown` state that `mpssas_action_scsiio` tests before the requeue). Total bound
  under 5 s.
- **Test (host):** after `mps_xnu_suspend(shutdown)` submit an IO and assert it completes at once;
  assert the whole call returns within 5 virtual seconds with a mock IOC that never becomes
  READY (TF4 time budget).

## 3. Refuted or downgraded

- **cam M3 "TASK SET FULL parked for ever": refuted.** `IOSCSIParallelInterfaceDevice.cpp:1966-
  1990` starts a kernel thread (`SendFromResendTaskList`) exactly for the case of no other
  outstanding task. Passing 0x28 through is fine.
- **C2 trigger "handles permute after a diag reset": downgraded.** `docs/design.md:504-505`
  shows handle = 0x9 + PHY on this firmware. The finding stays critical through the same-bay swap.
- **memory M3 (stale pointers after a failed reallocation in reinit): medium → low.** Needs
  IOCFacts to change across a reset (firmware flash) and an allocation failure. NULL the pointers
  in `mps_iocfacts_free` anyway.
- **locking F6 (setPowerState blocks ~75 s): merged into H5** (bound the quiesce).
- **callouts M1 (DELAY drops the mutex): medium → low (L11)**; its real consequences are listed
  separately.
- **locking F1 / callouts H1 severity kept high, reachability qualified:** needs TM timeouts,
  which C1 currently prevents.
- **The first reading of the panic ("no threads inside the kext"): confirmed**, with additions in
  section 5.

Checked and agreed with the area reviews (not repeated): exactly-once completion, CAM status
mapping, held-queue ordering, msleep/wakeup atomicity, callout arm/cancel bookkeeping, the
4d64411 taskqueue fix, lock order (mps_mtx → fLock / done_lock / tq_lock), IOVA use everywhere,
32-bit fields served by 32-bit tags, LUN and CDB bounds.

## 4. Test-fidelity improvements (what would have caught 4d64411, a8dc082 and the above)

- **TF1 (highest value):** one `HostThreadCall` with xnu semantics (enter while running starts a
  concurrent invocation; cancel true only when pending) used by the taskqueue, callout, hotplug
  and done calls; split the IOKit-free parts of the kext (`mps_kext_*`, the `Hotplug()` and
  `DeliverCompletions()` loops) into a host-compilable file and test them against a fake family
  that (a) only times tasks given to `SetTimeoutForTask`, (b) asserts no completion after
  `DestroyTargetForID`, (c) retries only READ/WRITE. Catches C1, H1, M6, M7, L1.
- **TF2:** asynchronous mock IOC: a doorbell write only queues the request; replies come later,
  in any order; reply and sense frames are poisoned when returned. Add device identity to the
  mock (handle ↔ disk can change across reset or swap): catches C2.
- **TF3:** pthread mode under TSan with real mutex/condvar (non-sticky wakeups), a callout timer
  thread and seeds; or, in the single-thread model, make every final unlock a seeded preemption
  point and erase `woken` at sleep entry. Catches H2, M1 and the 4d64411 class.
- **TF4:** virtual-time budgets: `mps_free`, suspend(shutdown) and StopController must finish in
  10 virtual seconds. Catches M2, H5.
- **TF5:** barrier contract (`mps_os_wmb` recorded by the mock per doorbell write). Makes H3
  testable.
- **TF6:** strict malloc: fail the Nth allocation over attach/reinit/hot-plug, poison non-zeroed
  memory, check free sizes, KASSERT "log and continue" mode under ASan. Catches M3, L4, L12.
- **TF7:** DMA: 64-bit tags above 4 GiB, a run that crosses 4 GiB, 16 KiB page mode (M5).

## 5. The restart panic of 2026-11-20 03:17 (build 386F7D9D)

What the report shows (stackshot parsed from the .panic file; `lastRunTime` is seconds before the
panic):

- Panic string `Halt/Restart Timed Out`: the 30 s timer armed in `PEHaltRestartInternal`
  (`iope.cpp:871-884,1049-1056`) before `handlePlatformHaltRestart`. The panicking thread is that
  timer's thread call.
- No frame of any thread is inside our kext. The only "image 13" frames are the zero terminators
  of launchd's stacks. The kext's work-loop thread (`SAS2308HBA`, tid 147861) is idle; it last
  ran 25.2 s before the panic, i.e. our last interrupt came about 5 s after the halt began.
- launchd thread 239955 (named "executing shutdown stall task") is the thread inside the reboot
  system call: blocked uninterruptibly in IOKit for 17.6 s, without a deadline.
- Four thread-call threads are blocked `TH_UNINT` in `IOCommandGate::commandSleep` under three
  Apple kexts (images 9, 10, 11 = UUIDs f5173fbb…, 4d83eac0…, 37b96595…): two for 30.0 s (since
  the halt began), two for 19.2 s. The 19.2 s pair has the shape
  thread call → kext 9 → kext 10 → kext 9 → `runAction` → kext 9 → `commandSleep`, which is what
  SAM's `sPowerManagement` → `IOSCSIBlockCommandsDevice::HandlePowerChange` → `SendCommand` →
  `GatedWaitForTask` (`IOSCSIPrimaryCommandsDevice.cpp:1250`, untimed) looks like. **I could not
  identify the three kexts from the file alone, so this attribution is a hypothesis.** It is one
  command away from being settled: on the Mac, after the benchmark,
  `kmutil showloaded --show loaded | grep -i -e f5173fbb -e 4d83eac0 -e 37b96595`.

Assessment:

- **Not the cause:** a missing acknowledgement (we call `super::systemWillShutdown`,
  `SAS2308HBA_PM.cpp:128`), a thread blocked in our quiesce or in `mps_free` (no kext frames), a
  stuck `StopController`.
- **Can cause exactly this picture (no kext frames, Apple threads asleep for ever):** IO that our
  HBA accepted and never completes. Two mechanisms exist in the code, both in build 386F7D9D and
  both unchanged in HEAD: (1) after the shutdown quiesce all new IO, and the R/W retries of IO
  the quiesce failed, are held with nothing left to release them (H5); (2) no IO timeout at all
  (C1). The last interrupt at T-25 s fits a quiesce that ended then, with SCSI-stack threads
  left waiting. If kexts 9/10/11 turn out to be IOSCSIArchitectureModelFamily /
  IOSCSIBlockCommandsDevice / IOSCSIParallelFamily (or IOStorageFamily), the kext is the cause
  through H5. If they are display or Thunderbolt kexts, it is not involved.
- **Can contribute on another day:** a quiesce that outlasts the 30 s watchdog when the IOC is not
  OPERATIONAL at shutdown (diag reset path, H5).
- **Current build:** has all of it; M5c did not touch the shutdown path. Until H5 and C1 are
  fixed, restart only after unmounting the disks and unloading the kext.
