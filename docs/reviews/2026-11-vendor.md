### V4 Vendor branch topology (root of master) + one branch + per-import tags — KEEP topology, CHANGE tag (risk L)
- Decided: vendor/freebsd-mps = master's root commit; future imports are commits on that branch,
  merged into master; tag `vendor/freebsd-mps-8c9ce319` (renamed below).
- Comparison: FreeBSD (git era, committers-guide "Vendor imports"): one `vendor/<name>` branch
  per project, an **annotated** tag `vendor/<name>/<version>` per import, merged into main with
  `git subtree merge`; the vendor branch is an orphan history, the first merge uses
  --allow-unrelated-histories. OpenZFS in FreeBSD: `vendor/openzfs/master` + per-release branches,
  same subtree merge. Submodule: unusable (we modify the files). `git subtree add --squash` /
  `subtree split` of upstream history: would give upstream blame, but needs a full freebsd-src
  clone and a slow split; not worth it for 20 files. Our shared-root variant is equivalent for
  merging (merge base = previous import) and simpler (no unrelated-histories step, blame of
  upstream lines lands on the import commit).
- Issues: the tag is **lightweight** (`git cat-file -t` = commit): no tagger/date/message, ignored
  by `git describe`, easy to move by accident. Name carries the hash, not the release.
- Question: why not an annotated tag, e.g. `vendor/freebsd-mps/14.3.0` (FreeBSD's scheme; for a
  non-release pin, `vendor/freebsd-mps/main-<date>-<short>`), message = upstream URL + full hash?
  Re-tagging needs no history rewrite.
- Prelim: KEEP branch topology; CHANGE tag to annotated (name: open).

Answer: agree: CHANGE tag. Annotated `vendor/freebsd-mps/14.3.0` (message: upstream URL + full hash 8c9ce319fef765890ce518cab85d3a470b669849 + date); delete the lightweight `vendor/freebsd-mps-8c9ce319`. Non-release pins use `vendor/freebsd-mps/<branch>-<YYYYMMDD>-<short>`. Branch topology unchanged.

Check: agreed. Status: RESOLVED-CHANGE (annotated `vendor/freebsd-mps/14.3.0`, drop the lightweight tag, naming rule for non-release pins in VENDOR.txt).
